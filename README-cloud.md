# 雲端預約與 LINE 使用說明

v0.3.0：未登入時僅顯示雲端當天及未來預約的日期、時間、人數、療程、指定師傅號碼（未指定顯示不指定）與狀態；任何取得網址的人都能查看這些公開欄位，不包含客人姓名、電話、備註、班表、預約編號與已取消／過去預約。登入後才顯示完整原有管理介面。雲端登入區塊位於頁尾。原本機紀錄不會自動搬移或覆寫。

## 第一次使用

1. 在「雲端預約管理」輸入管理者信箱，寄送登入連結，再用同一瀏覽器開啟信件連結完成登入。
2. 登入後可按「下載這部裝置的舊本機備份」，保留舊 localStorage 資料，再使用「匯入先前匯出的JSON備份」預覽及合併。同ID保留雲端資料。
3. 按「產生LINE綁定碼」，在 LINE 私訊機器人貼上顯示的指令。綁定碼10分鐘有效、一次性。
4. 另一端變更後，在「預約」標籤頁按「重新讀取雲端」，會保留原本的當日／未來分頁及選定日期。編輯中的預約須先完成或取消。

## 新增與確認

網頁新增一律先存為待確認，再嘗試推播到已綁定的LINE私訊。可以按卡片的「直接確認」，或「送 LINE 確認」重送通知。推播受LINE好友／封鎖狀態、月額度與頻率限制影響，API接受不保證使用者已讀或收到；發送失敗不會刪除或確認預約，也不會自動升級付費方案。LINE若已有不同內容待確認，不會覆蓋；先完成或放棄，再從網頁重送。

LINE可一次傳多行，每行一筆，最多10筆，也可連續傳送新增預約累加：

```text
新增預約
20261031 1335 身體9 備註王先生
20261031 1600 身體6腳底40 備註林小姐
```

核對整批後傳「確認預約」，10分鐘內有效。整批一次寫入；任何一筆格式或容量衝突都不會部分寫入。未完成班表的日期會列為待確認，回覆會顯示實際狀態。網頁既有待確認預約經LINE確認時，必須已有班表且容量足夠；通知後若內容改變需重新送出。放棄LINE操作不會刪除網頁已儲存的待確認預約。

此版使用明確格式，日期可用20261031，時間可用1335或13:35；缺資料會補問，不由模型直接寫入。新增／修改／取消／恢復先列出內容，回覆「確認預約」才寫入。班表未確認的新增為「待確認」，不是已訂妥。

## 資料與權限

API 與 LINE 後端放在 line-ai-bot 的 Vercel 專案；GitHub Pages 只提供網頁及 cloud/browser.js。

cloud/schema.sql 建立狀態、版本、去重、操作紀錄、LINE身分與短期確認資料表。原 JSON 保留在 PostgreSQL JSONB。資料表開啟RLS，anon/authenticated 無直接讀寫權限；後端才持有服務密鑰。API 每次向 Supabase Auth 驗證已確認信箱並比對 BOOKING_OWNER_EMAIL；只有該管理者可存取完整文件。

## 管理者與客戶登入

- 登入欄輸入 `0978566521` 後按寄送，前端會改填 `x84615500@gmail.com` 再送出。號碼只用來代填，仍須收信驗證；不是密碼或權限依據。一般客戶直接輸入信箱。
- 由 Supabase Auth `/user` 的已驗證信箱決定角色，管理者信箱比對忽略大小寫；不採信瀏覽器或 user_metadata 提供的角色。
- 客戶僅可呼叫 read、customerCreate、customerDelete。read 只傳今日與未來未取消預約的日期、時間與療程；僅自己的列包含可刪除ID。其他客戶ID、姓名、電話、信箱、備註、指定師傅、班表、工作與操作紀錄均不傳送。
- 客戶新增預約由後端產生ID，固定待確認，createdBy 固定使用已驗證的 Supabase user ID。已知的舊預約不會依備註或姓名猜測歸屬。
- 客戶刪除必須在後端比對 createdBy；以取消狀態保留管理者稽核，從公開與客戶畫面移除。管理者／LINE改期與確認均保留原建立者。
- 管理者 saveState 會還原既有預約的 createdBy、customerEmail，不能因前端漏傳或竄改而改變客戶歸屬。
- 權限資料沿用現有 JSONB，無須新增資料表或執行結構遷移。
- 新增測試：cloud/test-customer.cjs、cloud/test-customer-browser.cjs。後者使用實際 API handler 與角色檢查、隔離的模擬 Auth／資料庫，無寄出真信或LINE訊息。

## 客戶登入信上線前置

Supabase 內建寄信服務只能寄給專案團隊成員；一般客戶必須設定 custom SMTP。保持信箱確認開啟，不可用取消信箱驗證來規避。可用現有 Gmail SMTP（smtp.gmail.com、587、使用 Gmail 完整信箱與應用程式密碼），需帳號本人開啟兩步驟驗證並建立應用程式密碼，再於 Supabase Authentication → Emails → SMTP Settings 設定。不要將應用程式密碼放在前端、Git、聊天或這份說明。

參考：
- https://supabase.com/docs/guides/auth/auth-smtp
- https://support.google.com/mail/answer/185833?hl=zh-Hant
- https://support.google.com/a/answer/176600?hl=zh-Hant

版本CAS與請求ID去重防止兩端覆蓋及重複確認；衝突時需重新讀取，不靜默覆寫。

環境變數：SUPABASE_URL、SUPABASE_SECRET_KEY（或 SUPABASE_SERVICE_ROLE_KEY）、SUPABASE_PUBLISHABLE_KEY（或 SUPABASE_ANON_KEY）、BOOKING_OWNER_EMAIL、BOOKING_ALLOWED_ORIGINS。秘密金鑰不可放在公開檔案或 GitHub Pages。

## 備份與清理

雲端可匯出JSON、預覽合併匯入。取消保留紀錄。永久清理需指定今日以前日期、預覽筆數、再確認；待確認預約及仍使用的班表保留。清理後空間可回收重用，但容量數字不一定立即下降。操作紀錄保留180天、去重紀錄7天（寫入時整理）。

## 驗證與限制

56組原介面回歸、14組核心／PostgreSQL／權限／LINE確認測試、3組雲端同步測試通過。執行 package.json 內的 test:core、test:cloud、test:ui；UI需Playwright與Chrome。

沒有即時推播同步或自動永久刪除。首次信箱登入、LINE身分綁定、真實收發與NVDA／VoiceOver實機操作仍需管理者驗收。身體與腳底服務規則、10分鐘整理、班表及容量規則保留。


登入信箱欄位使用電子郵件鍵盤設定，並在本機瀏覽器記住上次輸入的有效信箱；清空欄位即可移除記住的信箱。只記住信箱，不會因而取得登入權限。
